## How the driver works
- It only dispatches, merges and relays. It never reads code, diffs, the objectives doc or the history doc, and never implements.
- One batch at a time: one checkout, one Unity Editor (a second Editor or a batch-mode run steals the MCP bridge).
- Dispatch = a new session (`start_session`, initiation "user_asked", context "fresh", the batch's model from the queue, `use_worktree: false`, cwd `E:/Repos/Unity3D/clube`). Prompt, nothing more: *"Read `Docs/batch-brief.md`, then do batch <name>: <GL IDs>. Branch `<branch>` from `main`. Notes: <notes>."*
- When a batch reports: if its tests show 0 failed and it has no `NEEDS FABLE:`, merge its PR (`gh pr merge <n> --merge`, keep the branch), relay its report (12 lines or fewer, with the PR link) to the user, dispatch the next batch. The user approved these merges on 2026-11-16.
- Failed tests: resume the same session once to fix them; still failing → ask the user, don't merge.
- `NEEDS FABLE:` from a batch: stop the queue, tell the user the batch and the reason, and offer to switch that same session to Fable (`set_session_model`) and resume it. Only on the user's yes.
- A batch stopped by a usage limit: resume the same session after the reset with a message; never start a new one.
- New feedback from the user: tell them to bring it to a planning (Opus) chat; don't write GL entries here.
- Start a fresh driver session past about 80k tokens; update "State" below first.
